
# Ticknova - Frontend Design System V2.0

> 产品名称统一为 **Ticknova**。原设计稿中的名称不作为系统品牌；继续采用本文的 Warm Editorial Workspace 设计语言。

> **当前优先级（2026-10-22）**：用户最新的 [Ticknova 前端质量与交互强制规范](Ticknova 前端质量与交互强制规范.md) 将当前设计方向调整为 **Calm Precision SaaS**，并要求立即分阶段整改。本文及 V3 的 Warm Editorial 配色与业务布局是历史和兼容参考；当字号、对比、密度、组件行为与新规范冲突时，以新规范为准。Ticknova 品牌色、浅色优先以及权限、业务正确性仍须保留。

> 2026-10-22：用户已补充 [V3.0设计与质量规范](<Ticknova 前端设计系统与 UI 质量工程规范 V3.0.md>)、[前端开发工作流](前端开发工作流.md)、[AGENTS补充强制规则](AGENTS补充强制规则.md)及[组件清单](COMPONENT_INVENTORY.md)。接续开发必须一并完整阅读，以V3.0和用户最新要求作为新工作基线，本文V2保留作历史参照；安全、权限与业务正确性优先。用户的10条最终执行原则已纳入 `CODEX_EXECUTION.md`，待修事项和分阶段计划见第16篇。

## 1. 设计目标

项目：AI 智能工单与知识协同平台

设计语言：Warm Editorial Workspace

关键词：
温润、精致、极简、可读、协作、高效、人性化。

设计目标：
- 形成独立的企业 SaaS 产品品牌。
- 与 AgentOps 深色智能运维平台保持明显差异。
- 重视工作效率、内容阅读和知识协作。
- 将 AI 融入业务场景，而不是仅提供聊天窗口。
- 对页面及所有 UI 组件保持统一质量标准。

禁止：
- 复用 AgentOps 的深蓝与电光蓝视觉体系。
- 使用赛博朋克、霓虹、玻璃拟态风格。
- 为了美观牺牲内容可读性。
- 随意堆叠无意义的 KPI 卡片。
- 将所有页面都设计为相同的 Dashboard 模板。
- 在业务页面硬编码局部品牌颜色或样式。

## 3. 页面设计规范

### 3.1 员工服务门户

采用 Search-first Layout。

主要内容：
- 全局问题搜索
- AI 智能问答入口
- 快捷创建工单
- 我的工单
- 热门帮助文档
- 常见问题分类

要求：
- 搜索是页面主要视觉焦点。
- 不暴露管理员或处理员功能。
- 表单路径简洁。
- 移动端优先保证搜索与提单体验。

### 3.2 工单工作台

采用 Inbox Workspace Layout。

包含：
- 工单队列
- 筛选与排序
- 个人待办
- 待分配工单
- AI 推荐信息

要求：
- 列表可以快速浏览。
- 信息层级清楚。
- 不通过大量卡片替代表格或工作队列。
- 筛选条件在返回列表后尽量保持。
- 列表刷新不得无故丢失滚动位置。

### 3.3 工单详情页

桌面端使用三栏布局：

左侧：工单信息与操作
中间：处理记录与交流时间线
右侧：AI Copilot 和相关知识

要求：
- 中间区域占最大宽度。
- 左右侧栏可以折叠。
- 回复用户与内部备注明显区分。
- 工单状态必须使用固定枚举映射。
- 变更状态应展示权限与状态限制。
- AI 不能绕过人工确认直接执行关键业务操作。

### 3.4 知识协同中心

采用 Editorial Document Layout。

主要功能：
- 知识分类树
- 搜索与筛选
- 文档阅读器
- 富文本编辑
- 版本历史
- 文档审核
- 权限标识
- 引用来源

要求：
- 阅读宽度优先考虑长文阅读舒适度。
- 标题、段落、列表、代码块层级清晰。
- 编辑与阅读模式明显区分。
- 长文档支持目录锚点。
- 内容保存状态始终可见。

### 3.5 数据分析页

采用轻量运营分析布局。

要求：
- 图表用于解释业务数据。
- 不能模仿 AgentOps 的实时监控大屏。
- 所有图表应有标题、单位和时间范围。
- 无数据时显示 Empty State。
- 图表加载失败时提供清晰的错误提示。

## 4. UI 组件实施标准

### 4.1 Button

必须覆盖：
- Primary
- Secondary
- Ghost
- Destructive
- Icon Only

必须实现：
- Default
- Hover
- Focus-visible
- Active
- Disabled
- Loading

约束：
- 图标与文字垂直居中。
- Loading 时防止重复提交。
- Disabled 不得依赖颜色作为唯一提示。
- 纯图标按钮必须有可访问名称。
- 危险操作必须根据风险提供确认流程。

### 4.2 Input / Select / Combobox

要求：
- 正确关联 Label。
- 提供 Placeholder、Helper 和 Error。
- 校验错误在字段附近展示。
- 正确处理长文本。
- 支持鼠标与键盘操作。
- 失焦、清空、禁用行为一致。
- 下拉内容不得被父容器裁剪。
- 弹层不得超出可视区域。
- 异步搜索必须区分加载、无结果与失败。

### 4.3 Dialog / Drawer / Popover

要求：
- 层级统一。
- 具备符合交互语义的关闭机制。
- 模态弹窗打开后正确管理焦点。
- 关闭后尽可能恢复触发元素焦点。
- 弹窗内容过长时允许内部滚动。
- 不出现页面和弹窗双重异常滚动。
- 未保存的数据需要离开确认。
- 不得出现嵌套弹窗相互遮挡。
- 侧栏关闭后清理不再需要的临时状态。

### 4.4 Data Table

要求：
- Header 和 Cell 对齐。
- 工单编号不意外换行。
- 超长标题使用合理截断及查看方式。
- 状态、优先级标签样式一致。
- 排序、筛选、分页可组合使用。
- 分页数据由实际接口决定。
- 选择操作与当前数据状态同步。
- 批量操作显示选中数量。
- 删除或变更数据后更新列表状态。

必须包含：
Loading / Empty / Error / Populated 状态。

### 4.5 Rich Text Editor

要求：
- 工具栏状态与选区一致。
- 粘贴内容经过安全处理。
- 支持基本格式和快捷键。
- 自动保存状态清晰。
- 未保存时离开页面有提示。
- 保存冲突不能静默覆盖他人修改。
- 上传附件有进度和错误反馈。
- 阅读模式与编辑模式一致地渲染合法内容。

### 4.6 Toast / Alert / Tooltip

Toast：
- 成功、失败、警告语义明确。
- 避免相同消息重复堆叠。
- 错误信息不能只有模糊的“操作失败”。
- 重要持久性错误不能仅依赖自动消失的 Toast。

Tooltip：
- 不得遮挡重要操作。
- 支持合理的位置避让。
- 对可聚焦元素支持键盘焦点触发。

Alert：
- 提供清晰标题和下一步操作。
- 高风险信息需保持可读性。

### 4.7 Navigation

要求：
- 当前路由高亮。
- 菜单层级清晰。
- 折叠导航具有 Tooltip。
- 无权限菜单不得显示可执行入口。
- 路由变化时更新面包屑和页面标题。
- 不得使用无实际功能的导航元素。

## 5. AI Copilot 组件规范

AI 区域使用独立的柔紫色视觉体系。

必须支持：
- 正在生成
- 正常完成
- 用户中止
- 生成失败
- 重试
- 知识来源查看
- 人工确认
- 无可引用知识

AI 建议必须与真实业务结果区分。

知识引用应包含：
- 来源文档名称
- 可用的章节或页码
- 可访问的引用位置
- 用户当前是否具备查看权限

禁止：
- 伪造 AI 置信度。
- 伪造知识来源。
- 将模型建议直接显示成已执行的操作。
- 未经权限校验修改工单状态。
- AI 操作失败后仍显示成功。

## 6. 响应式设计

建议重点验证：

1920px：宽屏
1440px：标准桌面
1280px：较小桌面
768px：平板
390px：手机

原则：
- 桌面端优先支持复杂工单工作流。
- 中等屏幕允许折叠信息侧栏。
- 移动端允许侧栏转换为 Drawer。
- 不允许主内容被固定侧栏挤压到不可读。
- 不允许页面产生意外水平滚动。
- 不允许按钮文字被裁切。
- 不允许弹窗底部操作区不可访问。
- 移动端重点保证员工门户与基础提单流程。

## 7. 全局组件状态

所有适用组件都必须验证：

1. Default
2. Hover
3. Focus
4. Active / Selected
5. Disabled
6. Loading
7. Empty
8. Error
9. Success

并非每个组件都需要全部状态。
但每个组件必须明确自己支持哪些状态，
不支持哪些状态，以及对应原因。

页面必须处理：
- 网络断开
- 接口超时
- 会话过期
- 权限不足
- 数据不存在
- 数据已被他人修改
- 请求重复提交

不得用静态假数据掩盖这些情况。

## 8. Codex 前端修改流程

这是强制执行规则。

### 阶段一：修改前审查

开始修改前必须：

1. 阅读本设计规范。
2. 确认本次任务的业务目标。
3. 检查当前页面和共享组件。
4. 列出直接修改的文件与组件。
5. 列出可能被间接影响的页面。
6. 检查已有 UI 测试与截图基线。
7. 对大范围修改提出分阶段实施计划。

不得在没有明确影响范围时直接重构全局样式。

### 阶段二：修改实施

遵循以下顺序：

Design Tokens
    ↓
共享 UI Primitives
    ↓
业务组件
    ↓
页面布局
    ↓
交互逻辑
    ↓
响应式适配
    ↓
视觉回归与功能测试

原则：
- 优先修改共享组件解决共性问题。
- 不得为了单个页面破坏全局组件。
- 不得在多个页面复制相同 UI 逻辑。
- 不得随意使用 !important 覆盖样式。
- 不得无理由批量替换 Class。
- 不得在未审查影响范围时修改全局 CSS。
- 不得仅为通过截图测试而掩盖布局错误。

### 阶段三：修改后检查

必须检查：

[ ] 页面主体布局
[ ] 顶部导航
[ ] 侧边栏
[ ] 按钮
[ ] 输入框
[ ] 表单校验
[ ] Select / Dropdown
[ ] Dialog / Drawer
[ ] Tooltip / Popover
[ ] 数据表格
[ ] 状态标签
[ ] Toast / Alert
[ ] Loading / Empty / Error
[ ] 键盘导航
[ ] 焦点样式
[ ] 滚动行为
[ ] 内容溢出
[ ] 响应式布局
[ ] 主题样式（若启用）
[ ] API 请求与错误反馈

### 阶段四：自动化测试

优先使用项目已配置的：
- TypeScript 类型检查
- ESLint
- 单元与组件测试
- Playwright E2E
- 视觉回归测试
- 无障碍自动化检查

若测试基础设施不存在，
应先说明并建立必要的最小测试。

对关键页面建立稳定的截图基线。

不得以“测试命令未报错”代替浏览器检查。

### 阶段五：提交说明

每次重要前端修改都要汇报：

1. 本次修改目标
2. 修改的文件和组件
3. 新增或调整的 Design Tokens
4. 直接影响的页面
5. 间接影响的共享组件
6. 测试执行结果
7. 截图回归对比结果
8. 尚未解决的问题和风险

不允许在未验证的情况下宣称 UI 完全正常。

## 9. 验收门槛

任何页面交付前必须满足：

[ ] 视觉符合 Ticknova 品牌体系
[ ] 组件无明显错位、遮挡或溢出
[ ] 页面具有合理的信息层级
[ ] 所有操作入口有真实功能
[ ] 关键组件具备必要交互状态
[ ] 键盘与焦点行为符合预期
[ ] 表单与数据状态正确
[ ] AI 输出与人工操作边界清晰
[ ] 角色权限符合产品规则
[ ] 关键尺寸的响应式布局已验证
[ ] 已执行适用的自动化测试
[ ] 已检查被修改共享组件影响的其他页面

如果任意关键项未通过：
不得将任务标记为完成。
必须说明阻塞原因并保留待修复项。

---

## 10. 最高优先级原则

视觉一致性不等于组件完整性。

页面布局完成不等于前端开发完成。

必须同时保证：
- Visual Consistency
- Component Integrity
- Interaction Correctness
- Responsive Quality
- Accessibility
- Business Correctness

这六项共同构成前端质量验收标准。
