30. Codex 前端开发工作流
本章节是项目级强制约束。
30.1 修改前分析
每次涉及前端页面、组件、样式、路由或交互的任务开始前，Codex 必须：
1. 阅读本文档。
2. 阅读相关业务需求与接口契约。
3. 检查现有组件和页面
4. 检查现有组件、页面及相关业务逻辑。
5. 检查现有 API 契约、权限规则和状态定义。
6. 确认本次修改是否影响共享组件。
7. 列出直接受影响的页面与间接受影响的页面。
8. 检查已有测试、截图基线和已知缺陷。
9. 明确本次任务的验收条件。

修改前必须输出简要的影响分析。

不得在没有明确修改范围的情况下直接重构全局样式、替换组件库或批量修改所有页面。

## 30.2 修改范围分级

根据修改影响选择适当的验证范围。

### L1：局部内容修改

例如：
- 修复一个页面的文案。
- 调整单个图标。
- 修正局部间距。

要求：
- 检查目标页面。
- 检查受影响元素。
- 执行适用的基础验证。

### L2：业务组件修改

例如：
- 修改工单状态标签。
- 调整筛选器行为。
- 修改知识引用组件。

要求：
- 检查所有已知调用页面。
- 执行组件测试。
- 验证关键交互。
- 检查相关业务状态。

### L3：共享组件或设计 Token 修改

例如：
- 修改 Button、Input、Dialog。
- 调整全局字体或间距。
- 修改主题变量。
- 修改全局表格样式。

要求：
- 检查组件清单。
- 识别全部受影响页面。
- 执行相关组件测试。
- 执行关键页面视觉回归。
- 检查深浅色主题（如均已实现）。
- 检查响应式布局。

### L4：架构或大范围前端重构

例如：
- 替换 UI 组件库。
- 重构路由或状态管理。
- 修改全局布局。
- 调整多个核心页面的信息架构。
- 修改全局 CSS 体系。

要求：
- 先提交分阶段实施计划。
- 明确依赖变化和回滚方式。
- 先建立或确认测试基线。
- 分批修改，不得一次性无差别重写全部页面。
- 每批完成后执行测试。
- 完成后执行关键路径 E2E 与视觉回归。
- 明确报告未覆盖的风险。

## 30.3 实施顺序

复杂前端任务遵循以下流程：

1. 明确需求与验收标准。
2. 阅读设计系统和业务规则。
3. 检查现有实现。
4. 制定影响分析与实施计划。
5. 优先修复设计 Token 或共享组件中的根本问题。
6. 再调整业务组件。
7. 最后调整页面布局。
8. 执行功能测试与视觉回归。
9. 修复发现的问题。
10. 汇报验证结果。

禁止为了修复单个页面而随意修改全局组件行为。

禁止在缺少证据时使用大量 `!important`、重复覆盖样式或新增平行组件。

## 30.4 修改完成后的审查

每次修改完成后，必须检查：

- 页面主体结构。
- 页面标题与操作区。
- 顶部导航与侧边栏。
- 按钮和图标按钮。
- 输入框与表单校验。
- Select、Combobox 和 MultiSelect。
- Dialog、Drawer、Popover 和 Tooltip。
- 数据表格、排序、筛选和分页。
- 状态标签与优先级标签。
- Toast、Alert 和错误提示。
- 文件上传与处理进度。
- 富文本编辑器与知识阅读器。
- AI Copilot 与引用来源。
- Loading、Empty、Error 和 Success。
- 长文本、窄屏和滚动行为。
- 权限控制和操作结果。
- 键盘导航与焦点管理。

只检查当前页面，不代表共享组件已经通过验收。

如果共享组件被修改，必须检查它的其他主要调用页面。

## 30.5 修改报告

每次重要修改完成后，必须说明：

1. 修改目标。
2. 修改文件和组件。
3. 受影响页面。
4. 修改的 Design Tokens。
5. 执行的测试。
6. 实际测试结果。
7. 视觉回归结果。
8. 未覆盖的测试。
9. 已知问题和剩余风险。

不得仅以“已优化 UI”“已完成重构”作为交付说明。

# 31. 前端自动化测试规范

## 31.1 测试分层

项目应根据实际依赖和复杂度建立以下测试：

### 单元测试

使用 Vitest 等现有测试框架。

重点覆盖：
- 状态映射。
- 日期和时间格式化。
- 数据格式转换。
- 表单校验。
- 权限相关的 UI 逻辑。
- 分页和筛选逻辑。
- 业务状态转换。
- 错误处理逻辑。

### 组件测试

使用 Vue Test Utils 或现有组件测试方案。

重点覆盖：
- Props 和事件。
- 不同状态的渲染。
- 表单交互。
- Dialog 和 Drawer。
- Dropdown 与 Select。
- DataTable。
- 文件上传。
- AI Copilot 的消息状态。

### 端到端测试

使用 Playwright 或项目已有的 E2E 框架。

重点覆盖：
- 登录和角色权限。
- 员工提交工单。
- 工单处理和状态变更。
- 知识搜索和阅读。
- 文档上传与发布。
- AI 问答与来源引用。
- 管理员配置。
- 异常请求和操作失败。

不得为了引入测试框架而重复安装已有功能的依赖。

## 31.2 测试数据

- 测试数据应可重复生成。
- 不得依赖不可控的生产数据。
- 不得在测试中使用真实用户敏感信息。
- 测试数据应覆盖正常、边界和异常情况。
- Mock 数据必须与真实 API 契约一致。
- 不得通过修改断言来掩盖真实缺陷。

## 31.3 必须覆盖的异常情况

根据功能适用性，至少验证：

- API 返回空数组。
- API 返回无效数据。
- API 请求失败。
- API 请求超时。
- 网络中断。
- 会话过期。
- 权限不足。
- 数据不存在。
- 数据被其他用户修改。
- 重复提交。
- 部分操作成功。
- 文件解析失败。
- AI 生成中止。
- AI 检索无结果。
- 引用文档不可访问。

# 32. Playwright 视觉回归规范

## 32.1 测试目的

视觉回归用于发现代码修改引起的意外布局变化、文字溢出、遮挡、间距错误和组件状态变化。

视觉回归不是单纯追求截图完全相同，而是确认视觉变化符合预期。

## 32.2 关键页面基线

至少为以下页面建立稳定的截图基线：

1. 员工服务门户。
2. 管理工作台。
3. 工单列表。
4. 工单详情。
5. AI Copilot。
6. 知识文档列表。
7. 知识编辑器。
8. 知识审核与版本管理。
9. 用户与角色管理。
10. 队列管理。
11. 服务目录。
12. 审计记录。
13. 运营分析。

根据实际路由和业务模块调整列表，不存在的页面不需要强行创建。

## 32.3 关键组件基线

对于重要共享组件，建立独立的视觉测试：

- Button。
- Input。
- Select。
- Dialog。
- Drawer。
- Dropdown。
- Tooltip。
- Badge。
- DataTable。
- Pagination。
- FileUploader。
- Rich Text Editor。
- AI Copilot。
- Empty State。
- Error State。
- Loading State。

每个组件应覆盖其适用的主要状态，而不是只保存一个默认状态截图。

## 32.4 测试环境

截图测试应尽量固定：

- 浏览器版本。
- 视口尺寸。
- 字体加载状态。
- 测试数据。
- 动画状态。
- 时区。
- 页面初始状态。

对于日期、实时数据和动态内容，应使用可控的测试数据，避免无关变化导致大量误报。

## 32.5 Playwright 示例

以下代码仅作为配置和测试的参考，应根据项目现有结构调整。

```typescript
import { test, expect } from '@playwright/test';

test('工单列表页面布局稳定', async ({ page }) => {
  await page.setViewportSize({
    width: 1440,
    height: 1000,
  });

  await page.goto('/tickets');

  await expect(
    page.getByRole('heading', { name: /工单/ })
  ).toBeVisible();

  await expect(
    page.getByRole('table')
  ).toBeVisible();

  await expect(page).toHaveScreenshot(
    'ticket-list.png',
    {
      fullPage: true,
      animations: 'disabled',
    }
  );
});

注意：
- 示例中的路由和元素名称必须与实际项目一致。
- 如果页面需要登录，应使用项目已有的测试认证方案。
- 不得为通过截图测试而删除页面真实功能。
- 截图失败时应检查差异原因。
- 只有确认变化是有意且符合规范时，才能更新基线。
- 不得在没有检查差异的情况下自动接受所有新基线。
32.6 视觉回归验收
- [ ] 主要页面没有意外布局偏移。
- [ ] 标题和正文没有异常换行。
- [ ] 按钮组没有错位。
- [ ] 弹窗没有被裁切。
- [ ] 表格没有异常溢出。
- [ ] 页面滚动行为正常。
- [ ] 状态颜色与设计 Token 一致。
- [ ] 移动端没有意外水平滚动。
- [ ] 截图差异已经审查。
- [ ] 有意修改已记录。

33. 前端测试矩阵
测试范围	必须检查的内容	通过条件
视觉一致性	字体、颜色、间距、圆角	符合设计系统
组件状态	Hover、Focus、Disabled 等	状态符合定义
交互行为	点击、输入、选择、关闭	行为正确
数据真实性	数值、单位、状态	与实际数据一致
API 状态	加载、成功、失败、超时	状态切换正确
表格	排序、筛选、分页、批量操作	查询与展示一致
表单	校验、提交、重置	错误处理正确
弹层	焦点、遮罩、滚动	无遮挡与残留状态
AI 功能	生成、引用、中止、重试	不伪造结果
权限	菜单、页面、操作	与后端授权一致
响应式	桌面、平板、移动端	布局可用
无障碍	键盘、焦点、对比度	满足适用要求
安全	HTML、附件、错误信息	不产生明显安全缺陷
回归	受影响页面	无未解释的退化
如果某项不适用，应在测试报告中说明原因，而不是默认跳过。

34. 组件与页面的 Definition of Done
一个组件只有同时满足适用的要求，才能标记为完成。
34.1 组件完成标准
- [ ] 视觉符合设计 Token。
- [ ] Props 与事件定义清晰。
- [ ] 交互行为明确。
- [ ] 支持的状态已实现。
- [ ] 边界情况已考虑。
- [ ] 键盘行为合理。
- [ ] 焦点状态清晰。
- [ ] 长文本和窄屏表现正常。
- [ ] 错误状态能够正确显示。
- [ ] 没有明显的控制台错误。
- [ ] 适用的组件测试已通过。
- [ ] 文档已更新（如需要）。
34.2 页面完成标准
- [ ] 信息架构符合业务需求。
- [ ] 页面标题和主要操作明确。
- [ ] 主要数据来自正确的接口。
- [ ] 加载、空数据、错误状态完整。
- [ ] 所有可见操作具有真实行为。
- [ ] 权限限制正确。
- [ ] 页面不存在明显的遮挡或溢出。
- [ ] 适用的响应式布局已检查。
- [ ] 关键路径测试已通过。
- [ ] 共享组件的影响范围已检查。
- [ ] 视觉回归结果已审查。
- [ ] 未解决的问题已明确记录。
34.3 重大前端修改完成标准
- [ ] 已完成修改前影响分析。
- [ ] 已识别受影响的页面与组件。
- [ ] 没有无理由替换技术栈。
- [ ] 没有通过硬编码绕过设计系统。
- [ ] 相关测试已执行。
- [ ] 关键页面已进行浏览器检查。
- [ ] 视觉差异已审查。
- [ ] 未覆盖的测试已明确说明。
- [ ] 不存在未解释的关键回归。
- [ ] 变更记录和风险说明完整。
