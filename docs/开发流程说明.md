# 开发与贡献指南

本指南面向维护者和贡献者。项目定位、架构和启动方式见 [README](../README.md)，业务规则和接口以 [角色用例](02-角色用例与需求.md)、[API 契约](07-API契约.md) 与实际实现为准。

## 修改前

- 先确认变更范围，检查受影响的模块、调用方、迁移和测试；涉及共享组件或大范围重构时，先分析影响并分阶段实施。
- 保留显式角色、空间与队列授权、作者不可自审、审核与发布分离、工单状态机、幂等和乐观锁等业务约束。前端隐藏入口不能替代服务端授权。
- 使用 Flyway 递增迁移，避免在启动逻辑中静默修改数据库结构；保持依赖锁和公开许可证声明一致。
- 测试与演示使用隔离数据库。不得把 `.env`、密码、令牌、用户上传、数据库备份或浏览器验收截图提交到仓库。

## 前端修改规范

修改页面、组件、布局、交互、主题或样式前，先阅读以下资料并核对现有代码和路由：

- [设计系统入口](frontend/UI_DESIGN_SYSTEM.md) 与 [前端质量与交互规范](<frontend/Ticknova 前端质量与交互强制规范.md>)。
- [V3 设计与质量规范](<frontend/Ticknova 前端设计系统与 UI 质量工程规范 V3.0.md>)、[前端开发工作流](frontend/前端开发工作流.md) 与 [补充规则](frontend/AGENTS补充强制规则.md)。
- [组件清单](frontend/COMPONENT_INVENTORY.md) 与 [回归检查清单](frontend/UI_REGRESSION_CHECKLIST.md)。

以已经验收的 Ticknova 设计和当前 Design Tokens 为准；旧稿中的建议布局、色值和组件名称应结合当前实现理解。安全、权限及业务正确性高于视觉便利。

1. 先遵循设计规范和共享组件，再处理业务页面，避免重复实现；共享样式变化须检查全部主要调用页面。
2. 保持真实数据和交互，不用静态示例掩盖加载失败、缺失值、AI 来源或操作失败。AI 建议须保留引用及人工确认，不能伪造执行结果。
3. 根据组件实际用途覆盖加载、空、错误、成功、禁用及焦点等状态；检查键盘操作、可访问名称、文本溢出、响应式布局及失败后的输入保留。
4. 除页面主体外，还须检查受影响的弹窗、抽屉、菜单、下拉、提示、焦点和滚动行为；未保存变更、版本冲突及权限变化按现有业务规则处理。
5. 执行适用的功能、浏览器、视觉和自动化回归；不得删除测试或掩盖错误以通过验收。关键组件或页面验收未通过时，不得宣称完成。

## 本地验证

按变更范围选择适用检查。Windows 后端测试可在项目根目录执行（依赖 Docker）：

```powershell
.\scripts\Test-Backend.ps1
```

前端检查：

```sh
cd frontend
npm ci --ignore-scripts
npm run typecheck
npm run lint
npm test
npm run build
```

解析服务检查（需要 Python 3.12 和项目锁定的 uv）：

```sh
cd docling-service
uv sync --frozen
uv run --frozen pytest -q
```

根目录的 `node --test scripts/*.test.mjs` 检查运维脚本和测试隔离规则。浏览器验收入口及适用范围见 [测试矩阵与阶段门](12-测试矩阵与阶段门.md) 和 `scripts/Test-Browser.ps1`；运行前先核实其使用的临时服务与数据清理行为。截图如用于本地视觉检查，应存放在项目外并在核对后清理。

提交说明应描述具体行为变化、实际运行的检查、失败或未运行项及剩余风险。不能将计划值、历史测试或 mock 的表现当作本次验证或真实模型质量结论。
